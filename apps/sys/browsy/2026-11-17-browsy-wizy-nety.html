Plan · draft · 2026-11-17

Browsy hosts Wizy.
Personal, local, social — kept apart.

A privacy-first data mesh: Browsy is the extension that authenticates you (Authy) and hosts Wizy; Wizy manages your JSONs and derives recommendations; Nety carries only the social layer. Local data moves directly between permitted peers, session by session. Nothing personal leaves the device unencrypted.

01

Personal, local, social — and the apps in play

Three concentric worlds. The class of a field decides where it may live and who may read it; the app never decides that on its own.

P · personal

The world that never leaves

Journal answers, health and body data, identity proofs, precise location, private messages, keys.

  • Lives encrypted in the vault inside Browsy.
  • Only Authy (unlock/sign) and Wizy (derive, in memory) touch it.
  • Apps receive an answer or nothing — never raw personal JSON.
L · local

The world you share by permission

App portraits, extended profile fields, shared playlists, project data, circle posts.

  • Direct, peer to peer, at session start.
  • Encrypted per recipient, under a signed grant with an expiry.
  • Never routed through Nety; revoke stops future pulls.
S · social

The world you publish

Published posts, public profile, public app summaries, social recommendations.

  • Structured exactly like local data — the class tag is the difference.
  • Travels through Nety; may be mirrored by Central.
  • Publication is explicit consent, never a side effect.

04

flovePortrait — the real case, two scales

This is the shipped envelope today. It stays exactly the same for apps and Appy; Browsy/Wizy add owner, class, grants and signatures around it.

today

The envelope (Goddy reference)

{
  "schema": "flove-portrait/1",
  "app": "goddy",
  "version": 1,
  "generatedAt": "…",
  "lang": "en",
  "phrase": "…",
  "rows": [
    { "key": "from:to", "kind": "cell",
      "title": "from → to", "items": ["2"] }
  ],
  "completeness": { "layers": 7, "total": 9 },
  "stats": { "count": 7, "intensity": 0.62, "max": 3 },
  "consent": { "share": "app",
    "purposes": ["self-reflection", "export"] },
  "source": { "url": "https://flove.org/apps/metas/goddy.html" }
}

API: get · validate · consult · merge · selfTest · toSummary · toAgent. Appy renders it; the file is still downloadable.

extension

What Browsy adds around it

  • Owner + bundle: owner, bundleId, version, signature.
  • Class: L by default; public slices become S only by consent.
  • Paths: documents.goddy.rows; grants can narrow to prefixes/slices.
  • Grants: grantee, paths, capability, expiry, encrypted content key.
  • Enforcement: consult(grant) intersects the grant with consent.purposes.
  • Audit: pull/share/deny log local to Browsy.

Scale 1 · one portrait, one device. The app API does not change; the wrapper is additive.

Scale 2 · the same portrait across the mesh. The grant is the only bridge; Nety never sees L.

The flovePortrait API, explained

Every app exposes the same seven functions. They are the seam Browsy/Wizy hooks into; the app does not need to know about bundles or grants.

FunctionWhat it doesInput → outputWho calls it
get()Reads the live model and builds the portrait() → flove-portrait/1App UI, Browsy/Wizy capture
validate(payload)Checks schema, app id and rows(object) → {ok, errors[]}Appy import, Wizy, tests
consult(sel)Returns a filtered read-only view for a purpose({purpose, enforceConsent, from, to, kinds, group, maxItems}) → flove-consult/1Wizy projections, agents
merge(payload, opts)Writes a portrait back into the app(portrait, {mode}) → {ok, applied, mode}Import, restore, peer sync
selfTest()Runs get → validate → consult() → {ok, rows, consultRows, errors}?selftest, CI
toSummary()Returns the app's own summary model() → app modelAppy legacy, Wizy context
toAgent()Returns the agent block (prompt, schema, suggestions)() → floveAgentBlockMyWizy / Flove AI
What changes with Browsy: get stays; validate becomes the first gate; consult accepts a grant and returns only the intersection; merge only accepts a verified bundle; selfTest is the M1 acceptance test; toSummary/toAgent stay local unless their output is exported as D/L/S.
06

MyFamily — the first local data manager

MyFamily is the L use case of Browsy. Each person added is kept as P, L or S and used as L: P is private, L is shared with others locally (federated), S is public data. Permissions over a P2P network are another planned trunk.

P · private

Kept, not shared

The record — person id, name, relation, 7 trait groups with nuances, 5 raters, notes, subject-consent, version — encrypted in the vault.

L · used by default

Local federated

Chosen traits/raters shared with named peers or circles, with expiry, and only if the subject-consent state allows it.

S · public

Public card

A minimal separate artefact for the web-social path; never the raw record, nuances or children's data.

MyFamily is displayed as a use case on the browsy page ↗. Third-party questions B01–B10 are in browsy-questions.md; P2P permissions are a later trunk.

10

The 10 questions

Q1 · P/L/S field by field

Map every shipped JSON and app field to a class; default for new fields.

Suggested: P unless listed; L for portraits; S only for already-public fields.

Q2 · Permission unit

File, JSON path, array slice or field — one unit for v1 and the grant schema.

Suggested: JSON path with array ranges; fields later.

Q3 · Local net discovery

QR/endpoint, LAN, WebRTC, or Nety DHT for addresses only.

Suggested: manual endpoint + signature first; WebRTC second; never L over Nety.

Q4 · Revocation guarantee

TTL, rotation, no-copy, UI wording, re-encryption.

Suggested: forward-only; short TTL; rotate keys on removal.

Q5 · Supersafe bar

Unlock factor, at-rest format, memory rules, encrypted backup.

Suggested: WebAuthn + passphrase; P only in Browsy/Wizy memory.

Q6 · Authy identity set

Channels, levels, sessions, masks, recovery, Nety PeerId binding.

Suggested: Ed25519 root + proofs; self-backup; social quorum fallback.

Q7 · Derivation first

D0/D1 first, D2 spike, D3 consent; explanation; shareability.

Suggested: local by default; D3 per request; D4/D5 later.

Q8 · Others view

Projection vs recomputation; signer; inference; consent.

Suggested: O0 signed projection; O1 opt-in; O2 later.

Q9 · Bundle schema

Envelope, documents, consent, signature scope, portrait compatibility.

Suggested: flove-bundle/0.1; portraits in documents[]; Authy signs.

Q10 · Offline sync

Deltas, vector clocks/CRDT, tombstones, TTL, conflict display.

Suggested: bundle version + vector clock; last signed snapshot; surface staleness.

11

The privacy rules, kept

Invariants

  • P never leaves unencrypted; no P in an S bundle.
  • L leaves only as an encrypted projection under a signed grant.
  • S contains no P by construction.
  • Every outbound byte traces to a grant (local audit log).
  • Defaults private; widening is explicit.
  • Revocation is forward-only; copies cannot be recalled.
  • Every received document is signed and verified.
  • Wizy computes locally by default; remote needs consent.
  • Nety does not learn who pulls from whom locally.
  • Linking a channel never re-derives identity keys.

Threats still open

  • Coerced unlock and memory scraping.
  • Authorized peer who leaks on purpose.
  • Unrecallable copies after revocation.
  • Extension supply chain / store compromise.
  • XSS on flove.org reaching the bridge.
  • Metadata graph visible to Nety nodes.
  • Inference and model inversion from D3/D2.
  • Hijacked social recovery quorum.
  • Usability pressure producing over-broad grants.
